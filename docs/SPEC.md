## 1. 專案概述

### 1.1 產品願景

一款常駐在 Windows 桌面的 **3D AI 數位人偶**。使用者先用內建捏人系統打造專屬角色（寫實或動漫風），角色會在桌面上自由活動；使用者對角色說話或打字，角色把指令轉交給使用者綁定的 AI（雲端或本地模型），再以語音或對話泡泡回答，並**依每一則回答的內容即時演出對應的動作、表情與視線**。

### 1.2 三大功能模組

| 模組 | 說明 |
|---|---|
| **A. 捏人系統（Character Creator）** | 畫風 → 性別 → 體型 → 臉部與五官 → 身材細節 → 外觀 → 服裝 → 個性 → 存檔 |
| **B. 桌面人偶（Desktop Mascot）** | 透明視窗中的 3D 角色，會走動、坐在視窗上、被拖曳、睡覺等，使用真實骨架動畫 |
| **C. AI 代理人（AI Agent Bridge）＋ 表演系統（Performance）** | 綁定多家 AI，轉交指令；回答時由表演系統把內容轉成動作、表情、語音 |

### 1.3 不在第一版範圍內

- 多人連線、角色分享社群平台
- 手機版、macOS 版
- 角色代替使用者操作電腦（列為未來擴充）
- 成人內容（見 §11）

### 2.2 為什麼從 Unity 改為 Godot

v0.1 建議 Unity，是假設有一般開發團隊在 Windows 上使用 Unity 編輯器。D2（免費開源）與 D5（Claude 單人開發）兩項決定讓結論改變：

| 考量 | Unity 6 | Godot 4 | 對本專案的影響 |
|---|---|---|---|
| 開發者能否直接編輯專案 | 場景、Prefab 是龐大的 YAML，實務上要靠編輯器圖形介面操作 | 場景（`.tscn`）、資源（`.tres`）都是精簡、可讀的文字檔 | Claude 沒有圖形介面，**能直接寫出完整專案** |
| 雲端自動建置 Windows 版 | 需要 Unity 授權序號放進 CI | 免授權；Linux 上即可無介面匯出 Windows 執行檔 | 每次推送都能自動產出可測試的 `.exe` 給使用者下載 |
| Claude 自行驗證畫面 | 困難 | 可在容器中以軟體繪圖算出截圖，Claude 能看圖檢查 | 美術成果可以先自我檢查再交給使用者 |
| 開源專案相容性 | 引擎本身閉源；Asset Store 付費素材不能放進公開原始碼庫 | 引擎 MIT 授權，整個專案可完全公開 | 符合 D2 |
| 透明桌面視窗 | 需自寫 Win32 | 內建逐像素透明與滑鼠穿透 | 省工 |
| VRM 生態 | UniVRM 最成熟 | godot-vrm 功能完整（含 MToon、彈簧骨） | 足夠 |
| 生態系成熟度 | 較成熟（口型同步、動畫套件多） | 較少，部分需自寫 | 這是 Godot 的主要代價，已納入時程 |

**結論：改用 Godot 4.7 .NET 版**，以 C# 撰寫，Win32 與 HTTP 等功能直接使用 .NET 標準函式庫。M0 技術驗證會優先確認三件風險最高的事：①透明視窗與滑鼠穿透、②執行期載入 VRM、③共用動畫套用到不同角色（重定向）。

### 3.1 MakeHuman 授權分析（已查證原始碼庫）

來源：<https://github.com/makehumancommunity/makehuman>（`LICENSE.md`）

| 部分 | 授權 | 對我們的影響 |

### 3.2 MakeHuman 能提供什麼

| 我們的需求 | MakeHuman 對應能力 |
|---|---|
| 性別 | Macro modifier：Gender（連續滑桿），另有 Age、Muscle、Weight、Height、Proportions |
| 臉、五官 | 頭型、額頭、眉毛、眼睛、鼻子、嘴、耳朵、下巴、臉頰等數百個 target |
| 身材 | 軀幹、胸部（大小、緊實度、位置、間距）、腰、腹、臀、骨盆、上臂、前臂、手、大腿、小腿、腳、脖子；另有以公分為單位的測量 modifier |
| 骨架 | 預設骨架（含臉部骨骼）與精簡骨架；關節位置依體型自動重算 |
| 服裝 | MHCLO：衣服頂點綁定在身體網格上，身形改變時自動貼合 |
| 髮型、眉毛、睫毛、眼睛、牙齒 | 有內建素材 |
| 表情 | 以臉部骨骼 pose 定義，可烘焙成 blendshape |

### 3.3 整合方式：素材移植 + C# 自寫變形引擎

| 方案 | 做法 | 定位 |
|---|---|---|
| A. 外部編輯器 | 使用者用 MakeHuman 捏人 → 匯出 FBX → 我們的 App 匯入轉成 VRM | 進階使用者的額外匯入管道 |
| **B. 素材移植 + 自寫引擎** | 自寫轉檔工具把 CC0 素材轉成 Godot 資源；在 App 內以 C#（必要時 Compute Shader）實作「滑桿 → target 權重 → 頂點變形 → 骨架重算 → 衣服貼合」 | **正式方案** |
| C. 背景呼叫 MakeHuman | 夾帶 Python 執行環境並透過 socket 外掛操控 | 不採用 |

**淨室實作原則**：只依據 CC0 資料檔本身的格式（`modeling_modifiers.json`、`.target`、`.mhclo`、`.mhskel`）撰寫規格與程式，不翻譯 MakeHuman 的 AGPL Python 程式碼。如此我們自己的程式碼可以自由選擇授權（建議 MIT，見 §11）。

### 3.4 方案 B 技術細節

**離線轉檔管線（開發期執行，產出隨 App 散布）**

```
MakeHuman CC0 素材
  ├─ base.obj（基礎網格）
  ├─ targets/*.target（稀疏頂點位移）
  ├─ modifiers/*.json（滑桿 → target 組合規則）
  ├─ rigs/*.mhskel（關節位置以頂點群平均定義）
  ├─ clothes/*.mhclo（衣服頂點 = 3 個身體頂點的重心座標 + 偏移）
  └─ poses / expressions
        │  自寫轉檔工具（C# CLI；Blender 批次腳本輔助）
        ▼
Godot 資源
  ├─ BaseMesh.res
  ├─ Targets.bin（稀疏二進位打包）
  ├─ Modifiers.json（我們自己的 schema，含中英文名稱與分類）
  ├─ Skeleton.json（關節 ↔ 頂點群對應，骨骼直接命名為 VRM 人形骨架名稱）
  └─ Clothes/*.res
```

**執行期流程（捏人畫面）**

1. 拖動滑桿 → 計算每個 target 的權重（macro modifier 在多個 target 間做多維內插）。
2. `最終頂點 = 基礎頂點 + Σ(權重ᵢ × Δᵢ)`，目標每次更新 < 16 ms。
3. 依新頂點重算骨架關節與 bind pose。
4. 衣服依綁定資料重新貼合；重算法線。
5. 存檔：烘焙成單一網格 → 擺出各表情並擷取頂點差，產生表情 blendshape → 匯出 **VRM 1.0**。

**桌面模式只載入烘焙好的 VRM**，不跑變形引擎，執行期負擔最小。

### 3.5 寫實與動漫雙畫風（D1）

兩種畫風共用同一套變形引擎與骨架，差別在「風格層」：

| 層 | 寫實風 | 動漫風 |
|---|---|---|
| 基礎網格 | MakeHuman 原始比例 | 同一網格 + **風格化 target 組**（自製）：頭身比縮小、眼睛放大並上移、鼻子與嘴縮小、下巴變尖、脖子變細、手腳修長 |
| 眼睛 | 3D 眼球 + 寫實虹膜貼圖 | 平面化大眼：虹膜/高光/眼白分層貼圖（可換色、可動畫） |
| 材質 | PBR 皮膚（次表面散射近似） | **MToon** 卡通著色（godot-vrm 內建）＋外框線＋陰影色調 |
| 臉部陰影 | 自然光影 | 臉部法線修正，避免卡通臉出現髒陰影 |
| 頭髮 | 網格頭髮 + 半透明 | 色塊髮束 + 高光帶 + 彈簧骨 |
| 表情 | 細膩幅度 | 誇張幅度＋漫畫符號（汗滴、怒筋、紅暈、問號等貼片特效） |

另外提供兩條匯入路線補強動漫風品質：

- **匯入 VRoid Studio 匯出的 VRM**：VRoid Studio 是免費的動漫風捏人軟體，使用者自己做的角色歸使用者所有。
- **匯入任何 VRM**：須遵守該模型自帶的 VRM 授權資訊（App 會讀出並顯示，例如「禁止暴力表現」時停用相關動作）。

> 誠實評估：以寫實網格改造的動漫風，品質會介於「半寫實動漫」與 VRoid 之間。第一版先以風格化 target + MToon 達到「可用、好看」，第二版再評估專門的動漫基礎網格。

### 3.6 捏人流程（UI）

```
① 起始 ─ 選畫風（寫實 / 動漫）→ 選性別（男 / 女 / 自訂滑桿）→ 預設範本（每畫風 8+ 款）
② 體型 ─ 年齡、身高、體重、肌肉量、比例（頭身比）
③ 臉部 ─ 臉型 → 額頭 → 眉 → 眼 → 鼻 → 嘴 → 耳 → 下巴 → 臉頰
④ 身材 ─ 在「素體」狀態下調整（不穿服裝，只有貼身基本內衣，見 §3.6.1）
           胸、腰、腹、手臂、臀、屁股、腿…每部位有「簡易模式」與「進階模式」
⑤ 外觀 ─ 膚色、眼睛、髮型、髮色、眉型、睫毛、妝容
⑥ 服裝 ─ 另一個圖層，套在素體上：上衣、下身、連身、鞋、襪、配件；可調色；
           自動貼合身形。任何時候都能按「隱藏服裝」回到素體繼續改身材
⑦ 個性 ─ 名字、聲音、說話風格、表演風格（§6.6）、預設 AI
⑧ 存檔 ─ 寫入 .doll + 匯出 VRM；可另存為範本
```

功能需求：

- **CR-01** 所有滑桿即時預覽，支援還原/重做（至少 50 步）
- **CR-02** 左右對稱開關（預設開啟）
- **CR-03** 隨機產生（可鎖定特定部位）
- **CR-04** 鏡頭：旋轉、縮放、快速聚焦臉/上半身/全身
- **CR-05** 預覽動作：待機、走路、揮手，檢查穿模
- **CR-06** 可匯入 MakeHuman 匯出的 FBX、VRM 0.x / 1.0
- **CR-07** 中途切換畫風時保留五官與身材參數
- **CR-08** 身材與服裝分層：身材參數只屬於素體，服裝不會改變身材；改完身材後已穿上的衣服自動重新貼合
- **CR-09** 身材編輯時可一鍵切換「素體 / 穿著服裝」預覽，並可對照全身正面、側面、背面

### 3.6.1 素體與服裝分層（身材細節編輯）

角色由兩層組成，彼此獨立：

```
┌──────────────────────────────┐
│ 服裝層（可任意更換、可隱藏）   │  上衣、褲裙、外套、鞋襪、配件
│   ↑ 依貼合資料自動跟隨素體形狀  │
├──────────────────────────────┤
│ 素體層（身材的唯一來源）       │  所有身材滑桿只作用在這一層
│   + 固定的貼身基本內衣          │
└──────────────────────────────┘
```

- **編輯身材時只顯示素體**，不受衣服遮擋，可清楚看到胸、腰、臀、腿的真實線條。
- 素體固定穿著**貼身基本內衣**（緊貼皮膚、不影響身形判讀，可換顏色），不提供全裸。原因：本專案是公開散布的開源軟體，且會串接各家 AI 服務（使用政策禁止相關內容）；這也是 §11 內容政策的一部分。轉檔時會排除 MakeHuman 中與私密部位相關的 target（`genitals`、`bulge`、`nipple-*`）。
- 服裝層使用 MHCLO 式貼合資料（衣服每個頂點綁定在素體三個頂點上），所以**先調身材再穿衣、或穿了衣服再回頭改身材**，衣服都會自動跟著變形。
- 緊身衣物（緊身褲、緊身衣、襪子）直接由素體表面外擴產生，貼合度最好；寬鬆衣物（裙子、外套）以彈簧骨/布料物理呈現擺動。

#### 身材滑桿清單

以下對應 MakeHuman CC0 素材中實際存在的 target（已查證 `modeling_modifiers.json`、`measurement_modifiers.json`、`bodyshapes_modifiers.json`）。**簡易模式**每部位只顯示粗體項目；**進階模式**顯示全部。所有左右成對的部位預設對稱調整，關閉對稱後可分別調左右。

| 部位 | 滑桿 | 測量（公分）模式 |
|---|---|---|
| 整體 | **性別**、**年齡**、**身高**、**體重**、**肌肉量**、**比例（頭身比）** | 身高 |

## 6. 表演系統（Performance System）— 每則回應都有不同、合適的動作

### 6.1 設計目標

- **PF-01** 每一則回應都會依內容演出，不會只是站著動嘴巴。
- **PF-02** 動作要「合適」：內容是開心的事就雀躍，道歉就鞠躬，說明步驟就扳手指數一、二、三，講到「那邊」就指方向。
- **PF-03** 動作要「不重複」：同樣是「開心」，這次拍手、下次比耶、再下次轉圈；同一個動作每次的速度、幅度、左右手也略有不同。
- **PF-04** 不能拖慢回應：AI 一邊串流回答，角色一邊開始演，不等整段回答完。
- **PF-05** 任何 AI（包括不太聽話的本地小模型）都要能演，只是精緻度不同。

### 6.2 做法：送指令給 AI 時附上「表演規則」

是的——**每次把使用者的指令送給 AI 時，系統提示詞裡都會附上一段表演規則**，請 AI 在回答文字中插入簡短的表演標記。標記會在顯示泡泡與念出語音前被移除，使用者只看到乾淨的回答。

**採用「行內標記」而不是整段 JSON**，原因：AI 的回答是一個字一個字串流過來的，行內標記讀到哪裡就能演到哪裡；JSON 必須等整段完成才能解析，角色會呆站好幾秒。

標記格式（盡量短，節省 token、也讓小模型容易學會）：

```
⟨情緒:強度 動作 動作…⟩
```

AI 實際回覆範例（使用者問：「我明天要面試，好緊張怎麼辦？」）：

```
⟨worried:0.4 tilt_head⟩ 會緊張很正常啦，代表你很重視這次機會！
⟨encourage:0.7 fist_pump⟩ 我給你三個小撇步：
⟨explain count:1⟩ 第一，先把自我介紹念熟，念到不用想就說得出來；
⟨explain count:2⟩ 第二，準備兩三個你做過最得意的例子；
⟨explain count:3⟩ 第三，今晚早點睡！
⟨happy:0.8 thumbs_up⟩ 你一定沒問題的，加油！
```

角色看到的演出：歪頭擔心 → 握拳打氣 → 伸出一根、兩根、三根手指 → 比讚微笑。

**表演規則提示詞**（節錄，實際內容依角色個性與可用動作自動產生）：

```
你是桌面角色「{名字}」。回答時請在每句話（或語氣轉折處）前加上表演標記 ⟨…⟩：
- 第一個欄位是情緒與強度：{情緒清單}，強度 0–1。
- 後面接 0–2 個動作，只能從清單中選：{動作清單（依分類列出）}
- 依內容挑選最貼切的動作；同一則回答中不要重複同一個動作。
- 標記只用來表演，不要解釋標記本身。
```

為了節省費用，表演規則放在系統提示詞的固定開頭，在支援提示快取（prompt caching）的服務上可大幅降低重複送出的成本；規則長度控制在約 400 token 以內。

### 6.3 「語意動作」而不是「動畫檔名稱」

AI 選的是**語意**（例如 `explain`、`agree`、`celebrate`），不是某個動畫檔。程式端的「動作庫」把每個語意對應到多個變化版本，這是做到「每次都不一樣」的關鍵：

```
語意：celebrate（慶祝）
  ├─ 變體 A：拍手（輕快）
  ├─ 變體 B：雙手高舉歡呼
  ├─ 變體 C：原地小跳兩下
  ├─ 變體 D：比 Yeah + 眨眼
  └─ 變體 E：轉一圈（僅全身模式、空間足夠時）
```

**變體挑選規則（PerformanceDirector）**

1. 篩選：排除目前姿勢做不到的（坐在視窗上時不能跳）、空間不夠的、角色 VRM 授權禁止的。
2. 去重複：最近 10 次用過的變體降低權重。
3. 依角色「表演風格」（§6.6）與情緒強度加權。
4. 隨機挑選後再做**參數微調**：播放速度 ±15%、動作幅度依強度縮放、左右手鏡像、起始時間抖動。

### 6.4 分層疊加

一個瞬間的演出由多層同時組成，彼此獨立變化，組合數量非常多：

| 層 | 內容 | 來源 |
|---|---|---|
| 表情層 | 喜、怒、哀、驚、害羞…＋強度；眨眼 | 標記的情緒欄位 |
| 嘴型層 | 口型同步 | 語音音訊 |
| 頭部/視線層 | 看使用者、看手指的方向、思考時往上看、害羞時移開視線 | 情緒 + 動作 + 程序化 |
| 上半身手勢層 | 指、數數、比讚、攤手、托下巴… | 標記的動作欄位 |
| 全身層 | 跳、轉圈、鞠躬、坐下、走過來 | 標記的動作欄位（較少用） |
| **說話節奏層** | 依語音重音與句子節奏自動加入小幅點頭、手部輕擺、重心移動 | **程序化**，不需 AI 標記 |
| 特效層 | 愛心、汗滴、怒筋、閃光、問號、音符（動漫風較誇張，寫實風較收斂） | 情緒 |

即使 AI 沒給任何動作，「說話節奏層」也會讓角色自然地邊說邊比劃，不會僵硬。

### 6.5 時序同步

```
AI 串流文字 ──► 標記解析器 ──► 依標點切成「句段」
                                   │
                    ┌──────────────┼───────────────┐
                    ▼              ▼               ▼
                 TTS 合成        泡泡顯示       PerformanceDirector
                    │                               │ 動作排程在該句段
                    └────── 語音實際播放時間 ───────►│ 開始播放的時間點
```

- 動作在「該句話開始念出」時觸發，而不是在文字到達時觸發，確保嘴巴、手勢、語音一致。
- 僅文字模式下，依打字機效果的進度觸發。
- 第一個句段到達即開始演出；等待第一個字的期間播放「思考」動作，且依問題類型變化（程式問題 → 托下巴盯螢幕；情感問題 → 歪頭；計算 → 扳手指）。
- 動作之間以混合（blend）平順銜接；手勢做完會自然回到說話待機姿勢。
- 使用者打斷時，所有層平順淡出。

### 6.6 角色表演風格

捏人第 ⑦ 步可設定，影響變體權重與幅度：

| 設定 | 範例 |
|---|---|
| 活潑度（0–1） | 高：常跳、常比手勢；低：動作小、偏優雅 |
| 誇張度（0–1） | 動漫風預設偏高，寫實風預設偏低 |
| 個性範本 | 元氣、溫柔、酷、傲嬌、知性、慵懶（各自有偏好動作） |

### 6.7 備援機制（PF-05）

| 等級 | 情況 | 處理 |
|---|---|---|
| 1 | AI 正確輸出標記 | 完整演出 |
| 2 | 標記格式略有錯誤（拼錯動作名、括號不同） | 寬鬆解析 + 同義詞對照（如 `wave_hand` → `wave`）；不在清單中的忽略 |
| 3 | 完全沒有標記（AI 忽略規則） | **本地導演**：以關鍵字規則（中英文情緒詞、問句、道歉、數字列表、方向詞）判斷每句的情緒與動作；選配：用使用者的本地小模型做第二次標註 |
| 4 | 以上都沒有結果 | 說話節奏層 + 中性情緒，仍有自然的邊說邊比劃 |

每個 Provider 會記錄「標記遵守率」，遵守率太低時自動改用較簡化的規則提示或直接採用本地導演。

### 6.8 使用者直接要求動作

指令本身就是動作時（「跳個舞」「揮揮手」「坐下」），本地先判斷意圖並**立即執行**，不需要等 AI；同時仍可交給 AI 產生搭配的台詞。

### 6.9 動作庫規模與來源（單人美術）

第一版目標：**約 35 個語意 × 平均 3–5 個變體 ≈ 120 段動畫**，加上程序化層。

| 分類 | 語意範例 |
|---|---|
| 回應 | agree（點頭）、disagree（搖頭）、unsure（歪頭）、listen |
| 情緒 | celebrate、laugh、shy、sad、cry、angry、surprised、relieved |
| 說明 | explain、count（數數，參數 1–5）、point（方向）、compare（雙手比較）、emphasize |
| 社交 | greet、wave、bow、apologize、thank、encourage、thumbs_up |
| 思考 | think、remember、idea（靈光一閃）、confused、facepalm |
| 全身 | jump、spin、dance、stretch、sit_down、stand_up |

| 動畫來源 | 說明 |
|---|---|
| **程序化動畫**（自寫） | 點頭、搖頭、歪頭、視線、呼吸、重心移動、數數手指、指向（以 IK 指向任意方向）等，由程式即時生成，天生每次都不同 |
| CC0 動畫素材庫 | 收錄前逐一確認授權為 CC0 或允許在開源專案中重新散布 |
| Claude 以 Blender 批次腳本製作關鍵影格動畫 | 手勢類（揮手、比讚、拍手、鞠躬）較適合；可在容器中算圖自我檢查 |
| 使用者錄製（選配） | 以免費的影片動作捕捉工具錄製後轉成 BVH 匯入 |

> 注意：Mixamo 動畫不可單獨散布原始檔，**開源原始碼庫中不可收錄**；Unity Asset Store 付費動畫也不適用。

**未來擴充**：文字生成動作（text-to-motion）模型可以為任何內容即時生成全新動作，等開源模型的授權與執行效能成熟後評估。

## 10. 非功能需求

| 類別 | 需求 |
|---|---|
| 安全 | 金鑰 DPAPI 加密；日誌遮蔽金鑰；全程 HTTPS；**不蒐集任何遙測** |
| 隱私 | 對話只送給使用者選擇的 AI；本地模型模式完全離線 |
| 穩定性 | AI 或語音失敗不得讓角色當機；例外統一記錄 |
| 相容性 | VRM 0.x / 1.0；Windows 10/11；多螢幕；100%–200% DPI |
| 防毒誤判 | 不使用全域鍵盤 Hook；申請開源專案免費程式碼簽章（如 SignPath Foundation，需再確認申請條件） |
| 可維護性 | 模組以介面隔離；AI Provider、TTS、STT、動作庫皆可擴充 |
| 測試 | 非引擎邏輯（路由、標記解析、導演、存檔）以單元測試覆蓋；CI 每次推送都跑 |

## 附錄 A：名詞解釋

| 名詞 | 說明 |
|---|---|
| Target | 一組頂點位移量，套用在基礎網格上可改變形狀（例如「鼻子變高」） |
| Modifier | 使用者看到的滑桿，背後控制一個或多個 target 的權重 |

| MToon | VRM 標準的卡通著色 Shader |
| MHCLO | MakeHuman 衣服格式，可隨身形自動貼合 |
| 表演標記 | AI 回答中 `⟨…⟩` 形式的情緒/動作指示，演出前會被移除 |
| 語意動作 | 如 `celebrate`、`explain`，對應到動作庫中多個動畫變體 |
| Root Motion | 由動畫驅動角色位移，避免腳步滑動 |
| IK | 反向運動學，例如讓手指準確指向某個方向 |
| SSE | Server-Sent Events，AI 回覆串流的傳輸方式 |
| DPAPI | Windows 內建的資料加密 API |
